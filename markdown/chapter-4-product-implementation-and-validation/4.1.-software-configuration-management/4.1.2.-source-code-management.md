### GitFlow

El equipo aplica el modelo de ramas de Driessen (2010).

| Rama | Sale de | Se integra en | Propósito |
| --- | --- | --- | --- |
| `main` | — | — | Versión publicada. Solo recibe releases y hotfixes revisados. |
| `develop` | `main` | `main` (vía release) | Integración del trabajo terminado del sprint. |
| `feature/<nombre>` | `develop` | `develop` | Una historia de usuario, un Bounded Context o una sección del informe. |
| `release/v<X.Y.Z>` | `develop` | `main` y `develop` | Estabilizar una entrega: últimas correcciones y número de versión. |
| `hotfix/<descripcion>` | `main` | `main` y `develop` | Corregir una falla en lo publicado sin esperar al siguiente release. |

Ejemplos de ramas `feature` usadas en los repositorios:

* **Backend:** `feature/core`, `feature/hierarchical-staff-and-specialties`, `feature/backend-documentation`.
* **Informe:** `feature/requirements`, `feature/team-members-photos`, `feature/fix-c4-diagram-html-labels`.

Reglas de integración:

1. Toda rama `feature` se integra a `develop` mediante Pull Request.
2. Otro integrante revisa el Pull Request antes de aprobarlo.
3. En el backend, `./mvnw test` debe terminar sin fallos. En el informe, el PDF debe compilar con Typst sin errores.
4. `develop` pasa a `main` solo al cerrar una entrega, también por Pull Request (por ejemplo, el Pull Request #25 de `shiftiq-platform`).

### Semantic Versioning

Las entregas se etiquetan con Semantic Versioning 2.0.0 (Preston-Werner, s.f.), con el formato `MAYOR.MENOR.PARCHE`.

| Componente | Se incrementa cuando… | Ejemplo |
| --- | --- | --- |
| `MAYOR` | La entrega rompe la compatibilidad con la anterior (por ejemplo, cambia el contrato de la API). | `1.4.2` → `2.0.0` |
| `MENOR` | Se agrega una funcionalidad compatible. | `1.4.2` → `1.5.0` |
| `PARCHE` | Se corrige un defecto o un detalle sin agregar funcionalidad. | `1.4.2` → `1.4.3` |

Estado actual por repositorio:

* **Informe:** registra sus versiones desde `v1.0` en el Registro de Versiones del Informe.
* **Backend:** el artefacto Maven está en `0.0.1-SNAPSHOT`. La versión `1.0.0` se asignará con el primer release desplegado de la API.
* **Landing page:** se versionará desde `1.0.0` junto con la primera entrega formal del sprint.

### Conventional Commits

Los mensajes de commit siguen Conventional Commits 1.0.0 (Conventional Commits, s.f.):

```text
<tipo>(<alcance>): <descripción en inglés, en minúscula y en modo imperativo>

<cuerpo opcional: qué cambia y por qué>

<pie opcional: BREAKING CHANGE: ... o referencia a la historia>
```

| Tipo | Cuándo se usa | Ejemplo tomado de los repositorios |
| --- | --- | --- |
| `feat` | Nueva funcionalidad. | `feat(core): implement workshop specialties aggregate, persistence, services and REST controller` |
| `fix` | Corrección de un defecto. | `fix(security): restrict customer and employee profile writes to admin or self` |
| `docs` | Cambios solo en documentación. | `docs(style-guidelines): enhance branding and typography guidelines with color palette and iconography details` |
| `style` | Formato del código o del documento, sin cambio de lógica. | `style(typst): restore rounded table corners (radius: 5pt) and clean sans-serif typography stack` |
| `build` | Dependencias, Maven, Docker o compilación del PDF. | `build(pdf): compile final pdf report post merge with main` |
| `chore` | Mantenimiento sin impacto en el producto. | `chore(assets): add 1E2A78 color swatch for chapter 4` |
| `refactor` | Cambio interno sin alterar el comportamiento visible. | Se aplica con el mismo formato, por ejemplo `refactor(<contexto>): ...` |
| `test` | Agregar o corregir pruebas. | Se aplica con el mismo formato, por ejemplo `test(<contexto>): ...` |

El alcance nombra el Bounded Context o el módulo afectado (`iam`, `core`, `fleet`, `billing`, `database`, `landing`, `requirements`). Si un cambio rompe la compatibilidad, se marca con `!` después del tipo o con `BREAKING CHANGE:` en el pie.
