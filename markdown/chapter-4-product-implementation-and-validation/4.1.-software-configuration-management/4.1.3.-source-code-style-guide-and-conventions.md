# 4.1. Software Configuration Management

## 4.1.3. Source Code Style Guide & Conventions

Las convenciones de ShiftIQ buscan que el código de todos los integrantes se lea como si lo hubiera escrito una sola persona. Se aplican cuatro reglas generales a todos los repositorios:

* **Idioma:** los identificadores, los nombres de archivo, los comentarios técnicos y los mensajes de commit se escriben en inglés. Los textos que ve el usuario se escriben en español e inglés y nunca quedan fijos en la lógica.
* **Lenguaje ubicuo:** las clases, tablas y endpoints usan los términos del modelo de dominio del capítulo 2 (`Workshop`, `Branch`, `Appointment`, `WorkOrder`, `Quote`, `Voucher`, `Obd2Device`).
* **Codificación y formato:** todos los archivos se guardan en UTF-8 y se formatean antes de cada commit.
* **Commits:** siguen Conventional Commits, como se describe en la sección 4.1.2.

### Java y Spring Boot (backend)

El backend sigue la Google Java Style Guide (Google, s.f.-a) y la arquitectura por capas de Domain-Driven Design.

**Nomenclatura**

| Elemento | Convención | Ejemplo en `shiftiq-platform` |
| --- | --- | --- |
| Paquetes | minúsculas, un paquete por Bounded Context | `com.tuxlogic.shiftiq.platform.core` |
| Clases, interfaces, enums y records | PascalCase | `Workshop`, `BranchCommandService` |
| Métodos, variables y parámetros | camelCase | `isAuthorizedForBranch`, `workshopId` |
| Constantes (`static final`) | UPPER_SNAKE_CASE | — |
| Agregados | sustantivo del dominio, sin sufijo | `Branch`, `BranchSubscription` |
| Value objects | sustantivo o identificador tipado | `WorkshopId`, `TaxId`, `PersonName` |
| Comandos y consultas | verbo + sustantivo + `Command` / `Get...Query` | `CreateBranchCommand`, `GetBranchByIdQuery` |
| Eventos de dominio | sustantivo + verbo en pasado + `Event` | `BranchCreatedEvent` |
| Servicios de aplicación | `CommandService` / `QueryService` y su `Impl` | `WorkshopCommandService`, `WorkshopCommandServiceImpl` |
| Controladores REST | recurso en plural + `Controller` | `BranchesController`, `AppointmentsController` |
| Recursos REST (DTO) | acción + recurso + `Resource` | `CreateWorkshopResource`, `WorkshopResource` |
| Persistencia JPA | `PersistenceEntity`, `PersistenceAssembler`, `RepositoryImpl` | `BranchPersistenceEntity`, `BranchRepositoryImpl` |
| Pruebas | clase probada + `Test` | `BranchAnalyticsSnapshotTest` |

**Estructura de cada Bounded Context**

```text
<context>/
├── domain/model/          aggregates, valueobjects, commands, queries, events
├── application/           commandservices, queryservices (interfaces) e internal (implementaciones)
├── interfaces/rest/       controladores, resources y transform (assemblers REST)
└── infrastructure/        persistence/jpa (entities, assemblers, adapters)
```

**Reglas**

* El dominio no depende de Spring, de JPA ni de otro Bounded Context.
* Un contexto solo se comunica con otro a través de servicios de aplicación o de eventos de integración publicados en `shared.domain.model.events`. Nunca accede a los repositorios de otro contexto.
* Los endpoints se versionan bajo `/api/v1/` y usan sustantivos en plural y kebab-case (`/api/v1/authentication/password-recoveries`).
* Las excepciones se traducen a respuestas HTTP en un manejador global. El mensaje interno de la excepción no se devuelve al cliente.
* Los textos de error y validación salen de `messages.properties` y `messages_es.properties`.
* Las clases públicas y los servicios de aplicación se documentan con Javadoc.

### Base de datos y migraciones

| Elemento | Convención | Ejemplo |
| --- | --- | --- |
| Tablas | snake_case en plural, generadas por `SnakeCaseWithPluralizedTablePhysicalNamingStrategy` | `work_orders`, `branch_subscriptions` |
| Columnas | snake_case | `branch_id`, `snapshot_date` |
| Migraciones Flyway | `V<número>__<descripcion_en_snake_case>.sql`, una por cambio de esquema | `V14__create_workshop_specialties_and_staff_roles.sql` |

Una migración ya integrada a `develop` no se edita. Cualquier corrección se hace con una migración nueva.

### HTML (landing page)

El marcado sigue la Google HTML/CSS Style Guide (Google, s.f.-b).

* Etiquetas y atributos en minúscula, con valores entre comillas dobles e indentación de 4 espacios.
* Todas las imágenes llevan `alt` y los controles sin texto visible llevan `aria-label` (por ejemplo, el botón del menú y el selector de idioma).
* Los `id` en camelCase se reservan para los elementos que manipula JavaScript (`pageLoader`, `siteHeader`). Las anclas de navegación usan una palabra en minúscula (`#inicio`, `#planes`).
* Todo texto visible lleva un atributo `data-i18n` con su clave de traducción.

### CSS (landing page)

| Regla | Convención | Ejemplo |
| --- | --- | --- |
| Nombres de clase | kebab-case con metodología BEM (bloque, elemento y modificador) | `site-header__wrap`, `lang-switch--nav` |
| Estados | prefijo `is-` | `is-loading`, `is-done` |
| Colores y sombras | variables CSS en `:root`, sin valores sueltos repetidos | `--primary-navy: #112433`, `--primary-orange: #1E3A8A` |
| Tipografía | familia Outfit para todo el sitio | `font-family: 'Outfit', sans-serif;` |
| Indentación | 4 espacios | — |

Las utilidades de Bootstrap (`d-flex`, `fw-bold`) se usan para el espaciado y la alineación. Las clases propias se reservan para los componentes de ShiftIQ.

### JavaScript (landing page)

* Variables y funciones en camelCase, declaradas con `const` o `let` (nunca `var`).
* Cada sentencia termina en punto y coma.
* Las claves de traducción de `js/i18n.js` usan snake_case con prefijo de sección (`nav_inicio`, `nav_planes`).
* Las funciones con parámetros se documentan con JSDoc.

### TypeScript y Angular (aplicación web, planificada)

Se adoptará la Angular Style Guide oficial ([angular.dev/style-guide](https://angular.dev/style-guide)):

* Archivos en kebab-case con el tipo como sufijo (`work-order-list.component.ts`, `branch.service.ts`).
* Clases en PascalCase y selectores con prefijo de la aplicación (`app-work-order-list`).
* Los componentes no llaman a la API directamente: lo hacen a través de servicios, y un interceptor HTTP agrega el token en `Authorization`.
* Los modelos que viajan por la red respetan los nombres de los recursos de la API.

### Kotlin y Android (aplicación móvil, planificada)

Se adoptarán las Kotlin Coding Conventions ([kotlinlang.org/docs/coding-conventions.html](https://kotlinlang.org/docs/coding-conventions.html)):

* Tipos en PascalCase, funciones y propiedades en camelCase y paquetes en minúscula bajo `com.tuxlogic.shiftiq`.
* Las pantallas usan componentes de Material Design 3 (Google, s.f.-c).
* Los textos de interfaz se definen en `strings.xml` (español e inglés) y no se escriben dentro del código.
