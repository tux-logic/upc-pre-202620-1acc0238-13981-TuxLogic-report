# 4.1. Software Configuration Management

## 4.1.4. Software Deployment Configuration

Cada producto de ShiftIQ se publica en el destino que mejor se ajusta a su naturaleza. La siguiente tabla resume la configuración de despliegue.

| Producto | Repositorio | Destino | Artefacto | Disparador |
| --- | --- | --- | --- | --- |
| Landing page | [Shiftiq-Landing-Page](https://github.com/tux-logic/Shiftiq-Landing-Page) | Vercel | Sitio estático (raíz del repositorio) | Push a `main` |
| Plataforma backend | [shiftiq-platform](https://github.com/tux-logic/shiftiq-platform) | Proveedor de contenedores + PostgreSQL gestionado | Imagen Docker con el JAR de Spring Boot | Integración de `develop` en `main` |
| Aplicación web (planificada) | Por crear | Vercel | Build de producción de Angular | Push a `main` |
| Aplicación móvil (planificada) | Por crear | Distribución del paquete Android | APK / AAB firmado | Release etiquetado |

### Landing page

La landing no tiene paso de compilación. Vercel publica directamente los archivos del repositorio según el `vercel.json`:

| Propiedad | Valor | Efecto |
| --- | --- | --- |
| `framework` | `null` | No se usa ningún framework de compilación. |
| `buildCommand` | `null` | No se ejecuta un comando de build. |
| `outputDirectory` | `.` | Se publica la raíz del repositorio (`index.html`, `terminos.html`, `css/`, `js/`, `Imagenes/`, `Videos/`). |
| `cleanUrls` | `true` | Las páginas se sirven sin la extensión `.html`. |
| `trailingSlash` | `false` | Las URLs no terminan en `/`. |

Pasos de despliegue:

1. Se importa el repositorio en Vercel desde la organización `tux-logic`.
2. Vercel detecta el `vercel.json` y configura el proyecto como sitio estático.
3. Cada push a `main` genera un despliegue de producción, y cada Pull Request genera una URL de vista previa para revisarlo antes de integrarlo.

### Plataforma backend

**Imagen Docker**

La API se empaqueta con el `Dockerfile` del repositorio, en dos etapas:

| Etapa | Imagen base | Acción |
| --- | --- | --- |
| `build` | `maven:3.9.16-eclipse-temurin-26` | Descarga las dependencias (`./mvnw dependency:go-offline`) y genera el JAR con `./mvnw clean package -DskipTests`. |
| `runtime` | `eclipse-temurin:26-jre` | Copia solo el JAR, activa el perfil `prod` (`SPRING_PROFILES_ACTIVE=prod`) y expone el puerto `8080`. |

Separar las etapas deja fuera de la imagen final a Maven y al código fuente, lo que reduce su tamaño. Las pruebas se omiten en la imagen porque ya se ejecutaron con `./mvnw test` antes de integrar el Pull Request.

**Base de datos y migraciones**

* En producción, el perfil `prod` arma la conexión `jdbc:postgresql://${DATABASE_URL}:${DATABASE_PORT}/${DATABASE_NAME}?sslmode=require`, de modo que la conexión con PostgreSQL siempre viaja cifrada.
* El esquema lo administra **Flyway**. Al arrancar, la API aplica en orden las migraciones pendientes de `src/main/resources/db/migration` (de `V1__baseline.sql` a `V14__create_workshop_specialties_and_staff_roles.sql`).
* Hibernate solo valida el esquema (`spring.jpa.hibernate.ddl-auto=validate`). Si una entidad no coincide con las tablas, la aplicación no arranca, lo que evita publicar una versión inconsistente.

**Variables de entorno**

Ningún secreto se guarda en el código. El proveedor de hosting debe definir estas variables:

| Grupo | Variables | Uso |
| --- | --- | --- |
| Base de datos | `DATABASE_URL`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD` | Conexión a PostgreSQL con SSL. |
| Servidor | `PORT`, `SPRING_PROFILES_ACTIVE` | Puerto HTTP (8080 por defecto) y perfil `prod`. |
| Seguridad | `JWT_SECRET` | Firma de los JWT. Debe tener al menos 32 bytes en Base64; si no, la API no arranca. |
| Google OAuth | `GOOGLE_CLIENT_ID` | Inicio de sesión con Google. |
| Correo | `MAIL_USERNAME`, `MAIL_PASSWORD` | Envío de correos por SMTP (Gmail, puerto 587 con STARTTLS). |
| Pagos | `MERCADOPAGO_ACCESS_TOKEN`, `MERCADOPAGO_WEBHOOK_SECRET` | Cobros con Mercado Pago y verificación HMAC-SHA256 de sus webhooks. |
| Facturación electrónica | `FACTOS_API_URL`, `FACTOS_API_KEY` | Emisión de comprobantes ante SUNAT mediante Factos. |
| Imágenes | `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | Almacenamiento de las imágenes subidas por los usuarios. |
| Proxy inverso (opcional) | `SERVER_TOMCAT_REMOTEIP_INTERNALPROXIES` | Solo si el proxy del proveedor tiene IP pública, para resolver la IP real del cliente. |

El repositorio incluye un archivo `.env.template` como plantilla de configuración. El archivo `.env` real, con los valores secretos, está excluido de Git mediante `.gitignore`.

**Entorno local**

Para replicar el despliegue en la máquina de desarrollo se usa `docker-compose.yml`, que levanta dos servicios:

| Servicio | Imagen | Puerto | Configuración |
| --- | --- | --- | --- |
| `postgres-db` | `postgres:16-alpine` | `5432` | Base `shiftiq_db` con un volumen persistente (`postgres_data`). |
| `app` | Construida con el `Dockerfile` | `8080` | Se conecta a `postgres-db`, aplica las migraciones de Flyway y usa tokens de 15 minutos (acceso) y 7 días (refresco). |

```bash
export JWT_SECRET=$(openssl rand -base64 32)
docker compose up -d
```

Con la API levantada, la documentación interactiva queda disponible en Swagger UI (`http://localhost:8080/swagger-ui/index.html`).

### Servicios externos

| Servicio | Propósito | Configuración |
| --- | --- | --- |
| [Mercado Pago](https://www.mercadopago.com.pe/developers) | Cobro de suscripciones y pagos en línea. | Token de acceso y secreto del webhook. |

### Aplicación web y aplicación móvil (planificadas)

* **Aplicación web:** el build de producción de Angular se publicará en Vercel, igual que la landing. La URL de la API se definirá por entorno (`environment.ts` para desarrollo y `environment.prod.ts` para producción).
* **Aplicación móvil:** Android Studio generará el paquete firmado (APK para pruebas internas y AAB para Google Play). La URL de la API se definirá por variante de compilación (`debug` y `release`).
